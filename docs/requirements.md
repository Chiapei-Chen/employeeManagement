# 需求理解

## 我的假設

這是一個**公司內部、給人資部門使用的小型系統**：

- 使用者是少數 HR 人員，多數人只需要查閱，少數人負責新增與修改資料
- 員工資料約數百到數千筆
- 只在公司內部使用，但員工資料屬於個資
- 範圍只有員工的基本資料，不包含薪資、考勤、組織架構

## 從假設推導出的決定

| 假設 | 所以我決定 |
|---|---|
| 多數人查閱、少數人新增與修改 | 兩種角色：readonly 只能讀取、admin 可以新增與修改；權限用對應表管理，日後可以增加角色 |
| 員工資料有數千筆 | 列表要分頁，並提供 HR 最常用的查詢條件：關鍵字、部門、在職狀態、到職日 |
| 多位 HR 可能同時編輯同一筆資料 | 用樂觀鎖防止後送出的人蓋掉別人的修改 |
| 員工資料需要保留歷史 | 不提供刪除，改用「離職」狀態；狀態的變化有明確規則 |
| 員工編號、Email 用來識別同一個人 | 兩者都不可重複；員工編號建立後不可修改 |
| 員工資料屬於個資 | 預設拒絕的權限設計；權限調整後立即生效 |
| HR 人員會異動 | 補上最小範圍的帳號管理（作業未要求） |

## 需求沒有提及、由我判斷的情境

| 情境 | 目前的處理方式 | 理由 |
|---|---|---|
| 到職日是未來的日期 | 允許，狀態為 `active` | HR 通常會在新人報到前先建立資料 |
| 狀態改為 `resigned`，離職日是未來的日期 | 允許 | 員工提出離職後，HR 會先登記預定的離職日。缺點是「已離職」的人在離職日之前仍在上班；若要區分，可以再加一個「預定離職」狀態 |
| 已離職員工的其他欄位（姓名、部門…） | 仍然可以修改 | 離職後仍可能需要更正打錯的資料；狀態本身不能再變更 |
| 離職員工回任 | 建立一筆新的員工資料 | 保留原本的離職紀錄。**已知限制**：Email 的唯一性也包含已離職的員工，所以回任時不能沿用原本的 Email（見 README「如果再多一天」） |
